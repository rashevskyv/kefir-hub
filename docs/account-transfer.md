# Перенос профілю і наіграних годин між консолями

Робоча інструкція. Перевірено чужими руками (Erista → Mariko, duckbill / 4PDA / GBAtemp).
Наші гіпотези позначені як **Г**. Експерименти — як **Е**.

Мета: один профіль + його години + іконки/назви ігор + можливість далі копити час.
Не мета: злити два різні профілі в один.

Хабовський шлях: **бекап розшифровує на джерелі**, **рестор на цілі пише внутрішні файли через FS — Horizon сам шифрує ключами цієї консолі**. HacDiskMount / hactoolnet не потрібні. TegraExplorer — запас, якщо 00F0 зайнятий.

---

## 1. Що де лежить

Усі ID — system save на розділі **SYSTEM** (`SYSTEM:/save/<id>`).

| Save ID | Owner | Що всередині | Для переносу |
|---|---|---|---|
| `8000000000000010` | account | Профілі: ім’я, UID, аватар, baas/nas, токени зв'язку Nintendo Account | **Обов’язково** для профілів та прив'язки |
| `8000000000000011` | account | idgen (`context.bin` — стан генератора UID) | Консолеспецифічний генератор. **Не є** прив'язкою акаунта та не є безумовно портативним між різними фізичними консолями. |
| `80000000000000F0` | ns / pdm | `pdm:/` Play Data. `PlayEvent.dat` — увімкнули, сон, пробудження, запуск/згортання ігор | **Обов’язково** для годин |
| `8000000000000041` | ns | LRU іконки HOME для недавно граних | **Г:** іконки в логу активності. Беремо, якщо на цілі іконки «Unknown» |
| `8000000000000120` | ncm | Кеш CNMT **прошивки** | **Не чіпати** — зламає OS |
| `8000000000000121` | ncm | Кеш CNMT ігор на **USER/NAND** | Не playtime. Копія на іншу консоль = «ігри встановлені, яких немає» |
| `8000000000000124` | ncm? | За повідомленнями — те саме для **SD** | Як 0121: не копіювати всліпу |

Години **не** в USER-сейвах ігор і не в JKSV-бекапі гри. DBI / NX-Activity-Log читають pdm (`pdmqry*`), дані живуть у **00F0**.

`PlayEvent.dat` — журнал подій по часу. Два профілі з **різних** консолей у один файл = накладки «в ту саму секунду запущено дві різні гри». Розшифровка в txt буває, пакувальника назад — ні. Тому **не мерджимо** профілі.

## 2. Крипт

Сирий файл `SYSTEM:/save/80000000000000F0` зашифрований ключами **цієї** консолі (BIS + save MAC). Вставити його в NAND іншої без перепідпису = TegraExplorer «скопіював, emuMMC не грузиться», розмір 0–1 КБ, Atmosphere crash.

Тому Хаб **ніколи не копіює сирий blob**. Він знімає **внутрішні файли** (Horizon сам розшифрував). На цілі Хаб відкриває **вже існуючий** system save через FS, пише файли всередину, `fsFsCommit()` — Horizon шифрує і підписує ключами цілі.

Два шари крипту, їх плутають:

1. **BIS** (розділ SYSTEM). TegraExplorer монтує його розшифрованим. Скопіювати файл `bis:/save/80000000000000F0` = підкласти **контейнер сейва**. Якщо контейнер ще з ключами джерела — brick. Це «покласти на розшифрований розділ».
2. **Save crypto** (NAX0 + CMAC `save_mac_key`). Саме його треба перепідписати під ціль.

TE `Save.commit()` у коді *вміє* flush + CMAC з `prod.keys` цілі (nx_savedata). Але це не Horizon, були баги flush v5, потрібні ключі на SD. Продуктовий шлях — запис Хабом через FS, як уже для 0010 / Linkalho.

Після 17.0.0 system save має бути в індексі FS (`8000000000000000`). Сире підкладання файлу в `SYSTEM:/save/` **минувши** CreateSave — ризик brick (SciresM). Скрипт **не створює** новий blob, якщо його немає.

`device_key` потрібен лише для ПК-репаку (додаток нижче). Для шляху Хаб + TegraExplorer — ні.

## 3. Шлях Кефіра (те, що в програмі)

Працює з **emuNAND** (рекомендовано) або sysNAND. Бекап SYSTEM цілі до будь-якого запису.

### 3.1. Бекап на джерелі (Horizon)

Tools → Users → **Backup profiles & play hours**.

Хаб **не вбиває** процеси. Він спершу намагається відкрити system save штатним read-only FS-шляхом і копіює **розшифроване** дерево на SD лише якщо Horizon це дозволив. Якщо сейв усе ще зайнятий — Хаб його пропускає, не завершує процеси і показує фактичний статус; `dump.te` лишається запасом лише для годин `00F0`.

```
/config/kefir/nand_transfer/<YYYYMMDD_HHMMSS>/
  manifest.json
  README.txt
  restore.te
  8000000000000010/     baas/, nas/, avators/, …
  8000000000000011/     якщо відкрився
  80000000000000F0/     PlayEvent.dat і сусіди
  8000000000000041/     якщо відкрився
```

Копія `restore.te` також лежить у `/config/kefir/nand_transfer/restore.te`.

Пак **зберігає UID**. Це не «Restore Backup» (той створює **нового** юзера і дописує години цього UID з ремапом, не замінюючи весь 00F0).

Якщо 00F0 не відкрився — закрити ігри, повторити. Без F0 профілі поїдуть, години ні.

### 3.2. Рестор на цілі (Хаб, Horizon шифрує)

1. Бекап SYSTEM цілі (Hekate).
2. Скопіювати всю теку пака на SD **цілі**.
3. Tools → Users → **Restore profiles & play hours**, обрати теку пака.
4. Хаб намагається відкрити наявні сейви на запис. Якщо Horizon утримує будь-який із них, Хаб не завершує системні процеси; для доступного сейву копіює внутрішні файли та викликає `Commit()`, а для зайнятого потрібно застосувати відповідний RCM/TegraExplorer fallback. Індекс FS не чіпаємо, новий blob не створюємо.
5. Ребут CFW. Перевірити профілі і DBI Activity Log.

Повна заміна F0 = години цілі **зникають**. Очікувано. Далі pdm пише нові події в цей журнал.

F0 без 0010 з тими самими UID = Unknown Players. Тому в паку обидва.

Якщо 00F0 не відкрився (зайнятий) — закрити ігри, повторити. Запас: TegraExplorer `restore.te` з пака (`readsave` / `write` / `commit`). Не копіювати сирий blob на BIS.

0121/0124 не копіюємо.

### 3.3. Офіційна прив'язка Nintendo Account з вбудованого донора (RomFS)

Tools → Users → Опції бічної панелі:
- **Link Nintendo Account** — прив'язка всіх незв’язаних профілів до офіційного донора Nintendo Account.
- **Unlink Nintendo Account** — зняття прив'язки (як у Linkalho): видаляє `baas`/`nas` цілей. Якщо є виділені профілі — лише вони (серед linked); інакше всі linked.

Також під час запуску Kefir Hub (тайтл, або альбом без згорнутої гри) пропонує прив'язати незв’язані профілі: пояснення + «Пізніше» / «Більше не нагадувати» (мінус) / «Прив'язати й перезавантажити». У альбомі зі згорнутою грою пропозицію не показує. «Більше не нагадувати» пише `account_link_prompt_skip` у конфіг; вручну лишається Tools → Users → Link Nintendo Account.

**Механіка роботи (Link і Unlink):**
- **Вбудований донор (RomFS)** для Link: `manifest.txt`, `baas/link.dat`, файли `nas/` з токенами.
- **Живий запис**: зупинка `BCAT`/`ACCOUNT`/`OLSC` → RW сейв `0010` → rollback на SD `/config/kefir/account_link_rollback/<stamp>/` → зміна `/su/baas` + `/su/nas` → `Commit` → soft reboot.
- **Link**: лише `linked_known && !horizon_linked`; already-linked не чіпаються.
- **Unlink**: видаляє baas цілей; nas для `nas_id` лише якщо жоден інший baas більше на нього не посилається.
- **Блокування**: applet + згорнута гра — Link/Unlink недоступні.

## 4. Два сценарії профілю

### A. Той самий UID (Backup profiles & play hours + restore.te)

0010 + 00F0 цілком. Лог активності показує імена, години як на джерелі, далі копиться.

### B. Новий UID (Restore Backup) — профіль + години цього юзера

Tools → Users → Options → **BACKUP & RESTORE USER**: **Backup user** (поточний профіль, або виділені галочками) і **Restore Backup**. Не в PROFILE і не в CONSOLE MOVE. Якщо пак цього UID уже є — Overwrite або Keep both. У списку рестору дата бекапу і чи є години; Minus видаляє пак з SD. Для Nintendo link пак має бути Linked (експорт читає 0010; якщо зайнято — terminate ACCOUNT).

Якщо цей Nintendo Account уже є на цілі (IPC або файл baas) — Хаб **замінює** той профіль, не створює другого. Інакше створює **нового** юзера. У `baas` перед записом підставляється UID цілі (байти 0..15); інші baas з тим самим nas_id стираються, лишається один файл. Два baas на один nas_id = `account` 2168-0006 і bootloop. Години: бекап знімає зріз `PlayEvent` цього UID. Рестор **не відкриває 00F0 на запис** (це User-Break `ns` / Atmosphere 2011-0301). Він читає 00F0 read-only, мерджить зріз у `/config/kefir/playtime_pending/PlayEvent.dat` і лишає `playtime_restore.te`. Запис у NAND — TegraExplorer. Restore Backup спочатку знімає 0010 (Horizon RO). Якщо зайнятий — `/startup.te` і TegraExplorer; скрипт сам дампить і повертає hekate. Відкат бутлупу: `hekate > payloads > tegraexplorer` (або `Undo_restore_if_wont_boot.te`); Undo стирає baas/nas, потім пише знімок. Backup після роботи ребутить сам.

## 5. Що перевіряти руками (пріоритет)

Робити на **emuNAND**, з бекапом SYSTEM.

| # | Дія | Очікування | Ломає? |
|---|---|---|---|
| **Е2** | Хаб: Backup profiles & play hours на джерелі | Тека з `PlayEvent.dat` і `baas/` | Ні, якщо тільки читання |
| **Е3** | На цілі: Хаб Restore тільки F0 | Години стали як на джерелі; профілі цілі | Години цілі |
| **Е4** | Е3 + 0010 з тими самими UID | Імена в логу, не Unknown | Профілі цілі = джерело |
| **Е5** | Тільки 0010, F0 не чіпати | Профілі змінюються, години цільові | Профілі |
| **Е6** | Restore Backup (новий UID) з `pdm/PlayEvent.dat` | Години нового профілю з'явились; години інших на цілі лишились | Ні, якщо 00F0 відкрився на запис |
| **Е7** | Пограти годину після вдалого Е4 | Час додається до старого журналу | Ні |

Що скинути з експерименту: чи відкрився F0 з Хаба, список файлів у паку, лог `restore.te` (wrote/errors), скрін DBI Activity Log до/після, чи є Unknown Players, чи копиться час.

## 6. Що не робимо

- Мердж двох повних PlayEvent.dat (два журнали консолі в один файл). Restore Backup дописує **зріз одного UID** з ремапом, не зливає два повні логи.
- Копія 0120/0121/0124 «щоб ігри підтягнулись».
- Сирий blob TegraExplorer / HacDiskMount без репаку ключами цілі.
- Перенос на чистий OFW / бан через онлайн із чужим pdm.

Ігрові сейви — окремо (вже вміємо: DBI zip + `fsCreateSaveDataFileSystem` на цілі). Вони не несуть годин.

## Додаток. ПК-шлях (якщо Хаб/TE не зайшов)

Потрібно: Hekate, Lockpick (з `device_key` на **обох**), HacDiskMount або NxNandManager, hactoolnet, `prod.keys` **джерела** і **цілі**. Бекап SYSTEM обох NAND.

```
hactoolnet.exe -k source_prod.keys -t save 8000000000000010 --outdir out/0010
hactoolnet.exe -k source_prod.keys -t save 80000000000000F0 --outdir out/00F0
hactoolnet.exe -k dest_prod.keys -t save dest_80000000000000F0 --repack out/00F0
```

На цілі: **видалити** старий blob, **потім** вставити вже перепідписаний. Не overwrite поверх.

Lockpick_RCM 1.9.11 на OLED інколи не знімає `device_key` — без нього ПК-репак на Mariko не збере. Для шляху Хаб + TE цей ключ не потрібен.
